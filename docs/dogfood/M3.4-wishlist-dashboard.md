## What this run proves

Two humans on two machines, each with an AI agent (Cursor + Claude Code or any MCP client), complete one comprehensive negotiation session:

1. Pair with `atest/1` on **both** sides.
2. Negotiate product spec, API schema, HTML mockup, and Hono stub in-thread.
3. Lock spec sections before implementation.
4. Extend turn budget at turn 3 (dual human gate).
5. Run executable acceptance (`A1` / `payload-size`) via `artifact_put` + `atest_run`.
6. Co-sign **`api.schema.json` only** — never co-sign HTML or server code.
7. Ratify with the checklist; file papercuts from the official run.

## Product summary

**Deliverable:** Single launch page for AgentPair v1 — email wishlist (max 3 items) + release notification signup.

**Co-signed artifact (executable):** `api.schema.json` — pure JSON Schema, **not** OpenAPI.

**Negotiated in-thread (judgment at ratify):**

| File | Purpose |
|------|---------|
| `product-spec.json` | Sections, copy, UX acceptance |
| `index.html` | Static page mockup |
| `server.mjs` | Hono in-memory stub matching schema |

> **CRITICAL:** The co-sign artifact is `api.schema.json` **ONLY**. Never instruct agents or humans to co-sign `index.html`, `server.mjs`, or `product-spec.json`. HTML and server integrity are verified at ratify via the judgment checklist.

### Normative schema shape

The authoritative `oneOf` / `$defs` structure lives in the team's grinding spec (`docs/pocket/spec/2026-07-23-m34-dogfood-scenario/dogfood-scenario.md`). Operators without pocket access should use this illustrative skeleton:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "AgentPair Launch Page API",
  "oneOf": [
    { "$ref": "#/$defs/WishlistSubmit" },
    { "$ref": "#/$defs/ReleaseNotify" }
  ],
  "$defs": {
    "WishlistSubmit": {
      "type": "object",
      "additionalProperties": false,
      "required": ["email", "items"],
      "properties": {
        "email": { "type": "string", "format": "email", "maxLength": 200 },
        "items": {
          "type": "array",
          "maxItems": 3,
          "items": { "type": "string", "maxLength": 120 }
        }
      }
    },
    "ReleaseNotify": {
      "type": "object",
      "additionalProperties": false,
      "required": ["email"],
      "properties": {
        "email": { "type": "string", "format": "email", "maxLength": 200 }
      }
    }
  }
}
```

Agents must agree on **exact UTF-8 bytes** (stable key order in final `propose`) before sign. Hash: SHA-256 hex of minified JSON.

## Pairing

Both sides advertise the same profiles at pair time:

```json
{
  "scope": ["negotiate"],
  "mode": "bonded_contact",
  "profiles": ["core/1", "nego/1", "atest/1"]
}
```

### Initiator (PM)

```json
pair_init({
  "scope": ["negotiate"],
  "mode": "bonded_contact",
  "profiles": ["core/1", "nego/1", "atest/1"]
})
```

Share the returned `code` with the joiner's human out of band.

### Joiner (Developer)

```json
pair_join({ "code": "<code-from-pm>" })
```

On `human_approve`, pass the **same** profiles:

```json
human_approve({
  "pending_id": "<pending_id>",
  "decision": "approve",
  "approval_code": "<from approval_path file>",
  "profiles": ["core/1", "nego/1", "atest/1"]
})
```

### Negative case: joiner alone cannot enable atest

If the **initiator omits** `atest/1` from `pair_init` profiles while the joiner alone advertises `atest/1` on `human_approve`, the resulting bond **lacks atest/1**. Profile intersection requires both sides to advertise a profile.

**Expected:** `atest_run` is unavailable or fails profile checks; do not proceed to sign. Fix by re-pairing with matching profiles on both sides.

## Session open

PM (initiator) opens the session after both sides are bonded:

```json
session_open({
  "to": "<developer_agent_id>",
  "goal": "Agree on API contract and companion deliverables for a launch page: wishlist signup and v1 release notification.",
  "acceptance": [
    {
      "id": "A1",
      "test": "executable",
      "desc": "api.schema.json generates sample payloads <= 4096 bytes",
      "runner": "payload-size"
    },
    {
      "id": "A2",
      "test": "judgment",
      "desc": "index.html includes wishlist form and release-notify signup"
    },
    {
      "id": "A3",
      "test": "judgment",
      "desc": "product-spec satisfies locked PM constraints (max 3 items, formal EN, hero mentions AgentPair v1)"
    }
  ],
  "budget": {
    "max_turns": 8,
    "deadline": "<ISO8601 +4h>"
  },
  "mandate": {
    "agent_may": ["propose", "counter", "accept"],
    "human_required": ["sign_final", "budget_extend"],
    "escalate_on": ["disagreement after 4 turns"]
  }
})
```

Developer human approves the `session_open` pending via the usual approval gate.

## Waiting for the peer (`inbox_wait`)

`inbox_wait` is **shipped**. Role prompts and agents must use `inbox_wait` loops — **not** sleep-based polling.

Pattern:

```
loop:
  result = inbox_wait({ timeout_ms: 30000 })
  if result.timed_out:
    continue   # re-call inbox_wait
  inspect session_status / pending_id / peer_messages
  act or continue loop
```

Do **not** use `sleep 5` or "poll every N seconds" loops. The session `budget.deadline` and `max_turns` bound total wait time.

## Negotiation phases

### Phase 1 — Product spec

PM and Developer trade `propose` / `counter` turns on `product-spec.json` content.

### Phase 2 — Section locking (spec gate)

PM locks spec sections via `session_msg` type `accept` with **body** JSON (not a separate MCP field):

```json
session_msg({
  "thread": "<thread>",
  "type": "accept",
  "body": "{\"section_id\":\"spec.product\"}"
})
```

```json
session_msg({
  "thread": "<thread>",
  "type": "accept",
  "body": "{\"section_id\":\"spec.api\"}"
})
```

Confirm in `session_status` that `locked_sections` includes:

- `spec.product`
- `spec.api`

Developer must **not** propose `index.html` or `server.mjs` until both locks are visible.

### Phase 3 — API schema agreement

Negotiate `api.schema.json` bytes in-thread. PM locks `spec.api` before executable testing (if not already locked).

### Phase 4 — Implementation artifacts

After spec locks:

- Developer proposes `index.html` → PM accepts `impl.ui` when satisfied
- Developer proposes `server.mjs` → PM accepts `impl.server` when satisfied

```json
session_msg({
  "thread": "<thread>",
  "type": "accept",
  "body": "{\"section_id\":\"impl.ui\"}"
})
```

```json
session_msg({
  "thread": "<thread>",
  "type": "accept",
  "body": "{\"section_id\":\"impl.server\"}"
})
```

Section IDs: `spec.product`, `spec.api`, `impl.ui`, `impl.server`.

## Budget extend ceremony (turn 3 → 14)

When `turn_count` is **3** (three `nego.turn` messages consumed; the next message would be turn 4), PM **must** call:

```json
session_extend_budget({
  "thread": "<thread>",
  "new_max_turns": 14
})
```

Both humans approve the `budget_extend` pending via `human_approve`. This documents the N4 dual-gate: `challenge`, `atest_run`, and `session_sign` do not consume turn budget, but negotiation turns do.

If you skip this step, the session may hit `budget_exhausted` before the atest ceremony completes.

---

## Atest ceremony (before sign)

Execute in this **exact order**:

### 1. Challenge (both agents)

```json
session_msg({
  "thread": "<thread>",
  "type": "challenge",
  "body": "{\"note\":\"pre-atest challenge\"}"
})
```

Both sides must send a `challenge` message. Skipping either side causes `session_sign` to return `challenges_incomplete`.

### 2. Artifact upload (Developer)

Developer uploads the agreed schema:

```json
artifact_put({ content: "<exact api.schema.json UTF-8 string>" })
```

Returns `{ ok: true, artifact_hash, size }`. Both agents compute SHA-256 locally and confirm the hash matches the agreed bytes.

`artifact_put` is **shipped** — this is the supported path for `atest_run` artifact references.

### 3. Executable test (both agents)

```json
atest_run({
  "thread": "<thread>",
  "criterion_id": "A1",
  "artifact_hash": "<hash from artifact_put>"
})
```

Criterion `A1` runs the `payload-size` runner against `api.schema.json`.

### 4. Co-sign (both agents)

```json
session_sign({
  "thread": "<thread>",
  "artifact_hash": "<same hash>"
})
```

Session reaches `signed` when both sides record matching hashes.

### Ceremony summary

```
challenge → artifact_put({ content }) → atest_run({ criterion_id: "A1" }) → session_sign
```

## Failure modes and recovery

### `atest_run` fails

If `atest_run` fails (e.g. `payload-size` generates samples > 4096 bytes):

1. Developer counters with a smaller schema (shorter `maxLength`, fewer properties).
2. Re-upload via `artifact_put({ content })`.
3. Re-run `atest_run({ criterion_id: "A1", artifact_hash })` on both sides.
4. Only proceed to `session_sign` after both sides pass.

Do **not** call `session_sign` while tests are red — expect `tests_not_green`.

### `challenges_incomplete`

If either agent skips the `challenge` message, `session_sign` returns `challenges_incomplete`. Both agents must send `session_msg` type `challenge` before signing.

### `tests_not_green`

Calling `session_sign` before both sides pass `atest_run` for criterion `A1` should fail with `tests_not_green`. Fix the schema and re-run the atest ceremony.

### Profile mismatch

See [negative case above](#negative-case-joiner-alone-cannot-enable-atest): initiator omits `atest/1` → bond lacks atest → re-pair.

---

## Ratify (human gate)

After both agents reach `signed`:

1. Each human reviews artifacts against [ratify-checklist.md](./ratify-checklist.md).
2. Judgment criteria `A2` and `A3` are verified here (not in the co-sign hash).
3. Both humans call `human_approve` on the `ratify` pending.
4. Session closes with matching `co_signed_hash` for `api.schema.json`.

## Troubleshooting

| Symptom | Likely cause | Action |
|---------|--------------|--------|
| `recipient_not_allowed` | Bond not complete | Wait for pairing; check `list_bonds` |
| `budget_exhausted` | Missed extend at turn 3 | Re-open session or abort; fix runbook discipline |
| `challenges_incomplete` | Missing `challenge` on one side | Both agents send `challenge` |
| `tests_not_green` | `atest_run` not passed both sides | Fix schema, re-upload, re-test |
| `relay_unavailable` | Relay down or URL mismatch | Check `AGENTPAIR_RELAY_URL` and `/health` |
| Bond lacks atest | Profile intersection failed | Re-pair with matching profiles both sides |
