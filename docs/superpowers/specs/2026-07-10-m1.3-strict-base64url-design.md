# M1.3 Strict base64url Decoding — Design

**Issue:** [#23 — M1.3 Strict base64url decoding (§3)](https://github.com/rfxlamia/agent-pair-protocol/issues/23)  
**SPEC:** §3 (lines 86–87)  
**ROADMAP:** M1.3  
**Status:** Approved  
**Date:** 2026-07-10

---

## Problem

SPEC §3 requires strict base64url decoding everywhere in the reference implementation:

> Implementations MUST reject padding characters, non-alphabet characters, and non-canonical encodings.

Commit `a4fbce3` introduced `decodeBase64UrlStrict` / `encodeBase64Url` and wired them into the envelope receive path (`envelope.ts`, `encrypt.ts`, `receive-envelope.ts`). Production code in other protocol modules still uses loose `Buffer.from(..., "base64url")` and `.toString("base64url")`, which accept padding and non-canonical forms.

## Scope

### In scope

- Entire `packages/protocol/` production source (`src/**/*.ts`)
- Export utilities from `@agentpair/protocol` public API
- Dedicated unit tests in `crypto/base64url.test.ts`
- Test helper cleanup in protocol test files (use exported encode util for valid fixtures)

### Out of scope

| Location | Owner | Notes |
|---|---|---|
| `relay/routes/inbox.ts` | M2.6 (#33) | Challenge-response sig decode + POST verify |
| `relay/routes/allowlist.ts` | M2.6 (#33) | Sig decode on allowlist push |
| `relay/routes/artifact.ts` | M2.6 (#33) | Sig decode on artifact routes |
| `mcp-server/relay/client.ts` | M2.1 (#28) | Encode-only; adopt `encodeBase64Url` during spillover work |
| `mcp-server/store/keys.ts` | Follow-up issue | Local key persistence; no current milestone |

**Close action for M1.3:** Amend M2.6 (#33) description to explicitly require relay adoption of strict base64url on **all routes** that decode or emit base64url (`inbox`, `allowlist`, `artifact`).

## Approach

**Approach A — Centralize + mechanical replace** (selected).

Single module (`base64url.ts`) owns strict rules. All protocol production code routes through it. Generic `Error` on failure; no new §10 error codes in this issue (deferred to M1.5).

Rejected alternatives:

- **B — Typed errors now:** Scope creep for `size:S`; §10 has no dedicated base64url code.
- **C — Pure non-Node implementation:** Over-engineering for the Node reference impl.

## API

```typescript
// packages/protocol/src/crypto/base64url.ts

/** Rejects padding, non-alphabet, non-canonical, and empty input per SPEC §3. */
export function decodeBase64UrlStrict(value: string): Uint8Array;

/** Canonical base64url encoding (no padding). */
export function encodeBase64Url(bytes: Uint8Array): string;
```

### Decode rules (existing implementation)

1. Reject empty string → `Invalid base64url encoding`
2. Reject characters outside `[A-Za-z0-9_-]` (includes `=`, `+`, `/`) → `Invalid base64url encoding`
3. Reject non-canonical: `Buffer.from(v, "base64url").toString("base64url") !== v` → `Non-canonical base64url encoding`

### Optional hardening

After strict decode in `agentIdToPublicKey`, reject if `bytes.length !== 32`. Noble curves throws later anyway; this fails fast and aligns with strict identity parsing.

## Public export

Add to `packages/protocol/src/index.ts`:

```typescript
export { decodeBase64UrlStrict, encodeBase64Url } from "./crypto/base64url.js";
```

Relay and mcp-server adopt in their respective milestones; M1.3 only provides the exported API.

## Error handling

Decode failures throw generic `Error`. Callers already map to existing paths:

- Envelope verify → `invalid_signature` or silent `false`
- `receiveEnvelope` → structured reject reasons
- PAKE decode failure → `pake_failed` flow

No new §10 error codes in M1.3.

## Testing

### New: `crypto/base64url.test.ts`

- Valid round-trip
- Reject: empty string, padding (`AA==`), standard base64 chars (`+`, `/`), non-alphabet
- Reject non-canonical encoding (alternate representation of same bytes)
- `agentIdToPublicKey("ed25519:AA==")` throws
- Optional: `agentIdToPublicKey` rejects decoded length ≠ 32

## Exit criteria

1. **Zero literal `"base64url"`** in `packages/protocol/src/**/*.ts` production code, except `crypto/base64url.ts` itself. Covers both decode (`Buffer.from`) and encode (`.toString`) paths.
2. `base64url.test.ts` passes.
3. Full protocol test suite green (`vitest run`).
4. `decodeBase64UrlStrict` and `encodeBase64Url` exported from `@agentpair/protocol`.
5. M2.6 (#33) issue body amended with explicit relay strict-base64url requirement.

## Dependencies

- **Blocked by:** M1.1 (sign-the-blob) — landed on current branch.
- **Blocks:** M1.6 golden test vectors (#26).

## Risks

| Risk | Mitigation |
|---|---|
| PAKE pairing breaks if relay sends loose encoding | PAKE payloads are encoded by our own `encodePakePayload`; strict decode only rejects attacker-supplied garbage |
| Relay remains loose until M2.6 | Explicit M2.6 amendment at M1.3 close; protocol host path is strict |
| `mcp-server/store/keys.ts` reads legacy local keys | Local file written by our encoder (canonical); loose decode of own output is compatible |
